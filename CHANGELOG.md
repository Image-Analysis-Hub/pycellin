# Changelog

All notable changes to Pycellin since version 0.5.1 are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

<!-- Planned v0.6.0. Covers commits up to 6b884a4, plus the documentation work of feature/docs up to 366d3c5 and the uncommitted removal of the time step checks of cycle lineages. Update from there with: git log 6b884a4..dev -->

Model merging and splitting, many new properties (morphology, intensity, topology), branch plots, consistent names that follow PEP 8, and many fixes, notably to time handling and to reading and writing TrackMate, GEFF, CTC and trackpy data. **This release contains breaking changes**, listed first below.

### ⚠️ Breaking changes

- **Naming:** `ID` is now written in lowercase in all Pycellin names, following PEP 8:
  - the core properties `cell_ID`, `lineage_ID` and `cycle_ID` are renamed `cell_id`, `lineage_id` and `cycle_id`, in DataFrames and exported files too. So are the `source_cell_ID` and `target_cell_ID` columns of `to_link_dataframe()`, the `pycellin_cell_ID` property of TrackMate exports and the `lineage_ID_Pycellin` column of trackpy exports, now `lineage_id_pycellin`
  - `Model` methods: `get_cell_lineage_IDs()` → `get_cell_lineage_ids()`, and likewise `get_cycle_lineage_IDs()` and `get_next_available_lineage_ID()`
  - the `ID_prop` argument of `CellLineage` and `CycleLineage` `plot()` and `get_tree_figure()` → `id_prop`
  - the fields of the `Cell` and `Link` named tuples (e.g. returned by `get_divisions()`), and the `node_ID`, `lineage_ID`, `source_lineage_ID` and `target_lineage_ID` arguments and attributes of exceptions
- **Naming:** arguments that abbreviated an ID are spelled out. Only calls that pass them by name break, except in the `Model` methods that now take lineage IDs by keyword only (see below):
  - `lid` → `lineage_id` (e.g. in `remove_lineage()` and `CellLineage()`), `lids` → `lineage_ids` (`get_divisions()`, `get_fusions()` and the `to_*_dataframe()` methods), `new_lid` → `new_lineage_id`, and `source_lid` and `target_lid` → `source_lineage_id` and `target_lineage_id`
  - `cid` → `cell_id`, `cids` → `cell_ids`, and `source_cid` and `target_cid` → `source_cell_id` and `target_cell_id`. In `CycleLineage.get_links_within_cycle()`, `ccid` → `cycle_id`
  - `nid` → `node_id`, e.g. in `is_root()`, `is_leaf()`, `get_descendants()` and the `compute()` method of calculators, and → `cell_id` in `Data.get_closest_cell()` and `get_closest_cells()`. `get_ancestors()` takes `node_id` in cell and cycle lineages too (`cid` and `ccid` before), so it is called the same way on both. Custom calculators can keep `nid` in their `compute()` method, since Pycellin passes the node ID by position
  - the `source_nid` and `target_nid` arguments and attributes of `TimeFlowError` → `source_node_id` and `target_node_id`
- **Naming:** the reading and writing functions follow PEP 8, with one verb pair: `read_*()` and `write_*()` for files, `from_*()` and `to_*()` for DataFrames:
  - `load_TrackMate_XML()` → `read_trackmate_xml()` and `export_TrackMate_XML()` → `write_trackmate_xml()`
  - `load_GEFF()` → `read_geff()` and `export_GEFF()` → `write_geff()`
  - `load_CTC_file()` → `read_ctc()` and `export_CTC_file()` → `write_ctc()`
  - `load_trackpy_dataframe()` → `from_trackpy()` and `export_trackpy_dataframe()` → `to_trackpy()`
  - `Model.load_from_pickle(path)` → `read_pickle(path)` and `model.save_to_pickle(path)` → `write_pickle(model, path)`
  - their modules are renamed alike, `loader` → `reader` and `exporter` → `writer` (e.g. `pycellin.io.geff.reader`), and the pickle functions are in `pycellin.io.pickle`
  - their file argument is `path` (`xml_path`, `geff_file`, `geff_out`, `ctc_path` and `ctc_file_out` before). Only the file or the DataFrame, and the model for the writers, can be given by position: the other arguments are keyword-only, e.g. `read_ctc(path, labels_path=...)`
- **Naming:** `reference_time_property` → `reference_time_prop`, since it holds the identifier of the property, like the other `*_prop` arguments: the `Model` attribute and argument, `set_reference_time_property()` → `set_reference_time_prop()`, the `ModelMetadata` field, and the argument and attribute (`ref_time_prop`) of the `Timepoint` calculator. `read_geff()` takes it too, instead of `time_prop`, like the new `reference_time_prop` argument of `read_trackmate_xml()` and `from_trackpy()`
- **Naming:** arguments and attributes that hold a property identifier are named `prop`, and those that hold a `Property` object `property`:
  - `get_property()`, `has_property()`, `remove_property()` and `add_pycellin_property()` take `prop` instead of `prop_identifier`, and `set_reference_time_prop()` instead of `prop_id`. Only calls that pass it by name break
  - `ProtectedPropertyError` takes `prop` instead of `prop_name` and stores it as `prop` instead of `property_name`, as does the new `MissingPropertyError`
  - calculators store their `Property` as `self.property` instead of `self.prop`, like their `property` argument: custom calculators that read `self.prop` must read `self.property`
- **Naming:** the lineage type of a property is `lineage_type` instead of `lin_type`, in `Property()` and on `Property` objects, and its values are lowercase like those of the property type: `"cell"`, `"cycle"` and `"both"` instead of `"CellLineage"`, `"CycleLineage"` and `"Lineage"`
- **Naming:** `single_type=True` leaves out the properties that have several types in every property getter: `get_cell_lineage_properties()` and `get_cycle_lineage_properties()` take it instead of `include_Lineage_props=False`, and `get_pycellin_cell_lineage_properties()` and `get_pycellin_cycle_lineage_properties()` instead of `include_Lineage_properties=False`, as `get_node_properties()` already did. By default, the properties of lineage type `"both"` are still returned
- **Naming:** more arguments spelled out or aligned with the rest of Pycellin:
  - `write_trackmate_xml()`: `img_path`, `img_path_field`, `img_shape` and `img_shape_field` → `image_path`, `image_path_field`, `image_shape` and `image_shape_field`
  - `add_cell()`: `global_cid` → `unique_in_model`, as in the new `relabel_cells()`
  - `add_lineage()`: `with_CycleLineage` → `with_cycle_lineage`
  - `get_ancestors()`: `sorted` → `sort`, which no longer shadows the built-in `sorted()`
  - `add_rod_length()`, `add_rod_width()` and the `RodLength` and `RodWidth` calculators: `skel_algo` → `skeleton_method` and `method_width` → `width_method`. `create_rod_length_property()` and `create_rod_width_property()` take an optional `custom_identifier`, as the other factories do, and `unit`, `custom_name` and `custom_description` by keyword only
  - `plot()` and `get_tree_figure()` of `CellLineage` and `CycleLineage`: `showlegend` → `show_legend`, like `show_horizontal_grid` and the new `plot_branch_profile()`
  - `Straightness.compute()`: `cycle_lin` → `lineage`, as in every other `compute()`
  - `LineageLocalPropCalculator.enrich()`: `lineages_to_enrich` → `lineage_ids_to_enrich`, since it takes lineage IDs
- **Naming:** metadata fields: `file_location` → `file_path`, the `TrackMate_version` field written by `read_trackmate_xml()` → `trackmate_version`, as `geff_version` and `pycellin_version`, and the `label_imgs_location` field written by `read_ctc()` → `label_images_location`
- **Naming:** the `Model` lineage getters are shorter, and the plural ones return all the lineages or those with the given IDs:
  - `get_cell_lineage_from_ID()` → `get_cell_lineage()` and `get_cycle_lineage_from_ID()` → `get_cycle_lineage()`
  - `get_cell_lineages_from_lin_prop(lin_prop, lin_prop_value)` → `get_cell_lineages_by_property(prop, value)`, and likewise for cycle lineages
  - the `get_lineage_IDs()` alias is removed: use `get_cell_lineage_ids()`
- **Naming:** lineages are called lineages wherever they are stored: `Data.cell_data` → `Data.cell_lineages` (also the argument of `Data()`), `Data.cycle_data` → `Data.cycle_lineages`, `Model.add_cycle_data()` → `add_cycle_lineages()` and `Model.has_cycle_data()` → `has_cycle_lineages()`. Custom global calculators that read `data.cell_data` must read `data.cell_lineages`
- **Naming:** `PropsMetadata.props` → `PropsMetadata.properties`, also as an argument of `PropsMetadata()`, since it holds `Property` objects
- **Naming:** `Model.get_units_per_properties()` → `get_properties_per_unit()`, which says what it returns
- **Naming:** names only meant for Pycellin's own use now start with an underscore, e.g. `check_literal_type()`, `check_fusions()`, `property_type_from_string()`, `property_type_to_strings()` and `ModelUpdater`. `pycellin.utils.is_equal()`, only used by the tests, moved to the tests, and `pycellin.utils.get_pycellin_version()` is replaced by `pc.__version__`
- **Exceptions:** the exceptions moved from `pycellin.classes.exceptions` to `pycellin.exceptions`, available as `pc.exceptions` (e.g. `pc.exceptions.UpdateRequiredError`)
- **Lineages:** `get_root()` always returns one node: it raises `LineageStructureError` when the lineage doesn't have exactly one root, instead of returning a list. The new `get_roots()` always returns a list, like `get_leaves()`
- **Lineages:** `CycleLineage.yield_links_within_cycle()` is removed: use `get_links_within_cycle()`
- **Lineages:** `CycleLineage()` no longer takes a `time_step` argument, unused since `cycle_duration` is computed from the reference time property alone: `CycleLineage(time_prop, time_step, cell_lineage)` → `CycleLineage(time_prop, cell_lineage)`
- **Properties:** `pycellin.graph.properties` moved to `pycellin.properties`, and its `tracking` module is now `timing`, except `is_complete_cycle`, now in `topology`. The `pycellin.graph` package no longer exists. `pycellin.properties` no longer exposes the calculators: import them from their module, e.g. `from pycellin.properties.morphology import RodLength`
- **Properties:** rename the `branch_*` properties to `cycle_*`, along with their `add_*()` methods, factories and calculators:
  - `branch_total_displacement` → `cycle_total_displacement`
  - `branch_mean_displacement` → `cycle_mean_displacement`
  - `branch_mean_speed` → `cycle_mean_speed`
- **Properties:** rename the `angle` property to `turning_angle`, along with its `add_*()` method, factory and calculator: `add_angle()` → `add_turning_angle()`, `create_angle_property()` → `create_turning_angle_property()`, `Angle` → `TurningAngle`
- **Properties:** rename the `ROI_coords` node property to `cell_contour` (TrackMate and CTC readers, all writers, sample GEFF data)
- **Properties:** rename four properties whose names could be misread, in DataFrames and exported files too:
  - `cycle_length` → `cycle_num_cells` (`create_cycle_num_cells_property()`): it counts the cells of a cell cycle, while the length of a cell cycle usually means its duration, which is `cycle_duration`
  - `level` → `generation` (`create_generation_property()`): the root cell cycle is still generation 0. Cycle lineage plots use it on the y-axis by default, and `to_cycle_dataframe()` sorts by it
  - `division_time` → `interdivision_time` (`add_interdivision_time()`, `InterdivisionTime`, `create_interdivision_time_property()`): it's the time between two successive divisions, not the time of a division
  - `cycle_completeness` → `is_complete_cycle` (`add_is_complete_cycle()`, `IsCompleteCycle`, `create_is_complete_cycle_property()`): it's a boolean, named like `is_division`
- **Properties:** `cycle_duration` values change: it is now the time elapsed between the first and last cells of the cycle, in the reference time unit. It was previously off by one frame and scaled by the time step a second time
- **Properties:** `cycle_total_displacement` is NaN instead of 0 for cell cycles without links, such as a cycle of a single cell
- **Properties:** rename the `custom_time_property` argument of `add_absolute_age()`, `add_cell_speed()`, `add_division_rate()`, `add_division_time()` (now `add_interdivision_time()`) and `add_relative_age()` to `time_prop`. Their calculators' `time_prop_name` argument is renamed to `time_prop` too, and the `use_div_time` argument of the `DivisionRate` calculator is removed
- **Properties:** `add_cycle_mean_displacement()`, `add_cycle_total_displacement()` and `add_cycle_mean_speed()` raise `MissingPropertyError` when the property they're computed from (`cell_displacement` or `cell_speed`) isn't declared yet: add it first. They now take the identifier of that property as first argument (`displacement_prop`, or `speed_prop` for `add_cycle_mean_speed()`), so pass `custom_identifier` and `include_incoming_edge` by keyword
- **Model:** remove the `Model.recompute_property()` and `Model.export()` stubs, which did nothing. Use the `pycellin.write_*()` functions
- **Model:** `add_cell()`, `remove_cell()`, `add_link()`, `remove_link()` and `split_lineage_from_cell()` take the lineage IDs, and the arguments after them, by keyword only, e.g. `model.remove_cell(5, lineage_id=0)`. Cell and lineage IDs are both integers, and these methods took them in different orders (`add_cell(lid, cid)` but `remove_cell(cid, lid)`), so a call written by analogy silently acted on another cell. `add_link()` now takes the two cell IDs first: `add_link(source_cell_id, target_cell_id, source_lineage_id=...)`. Calls written the old way fail with `TypeError`
- **Model:** `get_cell_lineage()` and `get_cycle_lineage()` (`get_cell_lineage_from_ID()` and `get_cycle_lineage_from_ID()` in 0.5.1) raise `TypeError` for a lineage ID that isn't an integer. A string or a lineage gave None, and a float or a boolean the lineage with an equal ID, e.g. lineage 1 for `True`. NumPy integers work, and an unknown ID still gives None
- **Model:** `add_lineage()` and `CellLineage()` raise `TypeError` for a lineage ID that isn't an integer, e.g. a float, a string or a boolean, and so does `split_lineage_from_cell()` for `new_lineage_id`. `CellLineage()` used to fail on an `assert`, which let booleans through, and these methods accepted any ID when given a lineage or a new ID, although a float or a string made TrackMate exports unreadable
- **Model:** Pycellin no longer gives a single-cell lineage minus the ID of its cell as lineage ID: like any lineage it creates, it gets the next free ID. This changes the lineage ID of a cell split off a lineage by `update()`, e.g. after `remove_link()`, and of the single-cell lineages read from a GEFF file without lineage IDs. `update()` also no longer gives the split cell a new ID when minus its ID was already a lineage ID
- **Model:** `add_cell()` no longer sets the `timepoint` of the cell: it is computed at the next `update()`, like the other properties. Models built from scratch now count timepoints from their earliest cell, as models read from files do: cells at 10, 12 and 14 min with a time step of 2 min get timepoints 0, 1 and 2 instead of 5, 6 and 7
- **Lineages:** rename `CellLineage.get_sister_cells(cid)` to `get_sisters(node_id)`, which also works on cycle lineages, where it returns the sister cell cycles
- **Plotting:** rename `node_color_scale` to `node_colormap` in `CellLineage` and `CycleLineage` `plot()` and `get_tree_figure()`
- **TrackMate:** `read_trackmate_xml()` takes `lone_spots` and `tracks` instead of `keep_all_spots` and `keep_all_tracks`, which name what it loads in TrackMate's terms: `lone_spots` is `"none"` (default), `"visible"` or `"all"` for the spots outside tracks, and `tracks` is `"visible"` (default) or `"all"`. Visible spots and tracks passed the spot and track filters of TrackMate (`VISIBILITY` of 1, listed in `FilteredTracks`). Replace `keep_all_spots=True` with `lone_spots="all"`, and `keep_all_tracks=True` with `tracks="all"`. `lone_spots="visible"` is new: it adds the spots outside tracks that TrackMate shows, without those its spot filters hid
- **TrackMate:** `write_trackmate_xml()` takes `space_unit` and `time_unit` instead of the `units` dict. They default to the units of the model, or to "pixel" and "frame", with a warning, when the model has none. The writer no longer asks for them with `input()`, which blocked scripts
- **CTC:** the reader now uses a new `time` property as the reference time property, instead of `timepoint`
- **CTC:** with label images (`labels_path`), cell positions and contours are now in the space unit: their pixel coordinates are multiplied by the pixel size. They were in pixels while the model had the space unit given to the reader, so properties computed from them, such as `cell_displacement`, got that unit for values in pixels
- **trackpy:** the reader now uses a new `time` property (frame × time step) as the reference time property, instead of `frame`, and renames the trackpy coordinates `x`, `y`, `z` to `cell_x`, `cell_y`, `cell_z`
- **Export:** `write_ctc()`, `write_geff()`, `write_trackmate_xml()` and `to_trackpy()` raise `UpdateRequiredError` when the model requires an update: call `model.update()` first. Most of them exported the changes not yet processed as they were, e.g. a lineage left in two parts by `remove_link()`, so a GEFF file written that way couldn't be read back correctly
- **Export:** `write_geff()` and `write_trackmate_xml()` return None, like `write_ctc()` and `write_pickle()`. They returned their working copy of the model, half converted for the file (e.g. in TrackMate's names, without `cell_id`): Pycellin couldn't always use it, and Jupyter displayed it and kept it in memory. To see what was written, read the file back
- **GEFF:** `write_geff()` no longer has a `variable_length_props` argument, which the "Getting started" notebook called mandatory: it never had any effect, since geff detects variable-length properties from their values. Just remove it from your calls
- **GEFF:** `read_geff()` is stricter with coordinate arguments: they must describe a complete 2D or 3D system (x and y, plus z in 3D), or it raises `ValueError`, e.g. for `cell_x_prop` alone, which 0.5.1 accepted. Inferred coordinates are each assigned at most once. A coordinate argument or `reference_time_prop` (`time_prop` in 0.5.1) naming a property that isn't on every node is now reported with a warning instead of an INFO message, before the property is inferred from the GEFF metadata
- **GEFF:** without `cell_id_prop`, `read_geff()` uses the `cell_id` property of the file as cell identifier when its values are unique non-negative integers, instead of always creating cell IDs from the GEFF node IDs. Without `lineage_id_prop`, it also looks for a `lineage_id` property when the GEFF metadata only declares a tracklet property
- **Pickles:** models pickled with Pycellin 0.5.1 can't be read, since modules moved (`pycellin.graph` no longer exists) and names changed (e.g. `cell_ID`, `cycle_length`): read their original files again
- **GEFF:** files written by Pycellin 0.5.1 keep the 0.5.1 property names when read, e.g. `ROI_coords`, and `cell_ID` beside the new `cell_id`, so methods that read the new names fail on them, e.g. `add_rod_length()`, which reads `cell_contour`. Read the files they were made from again
- **Exceptions:** Pycellin exceptions now subclass the matching built-in exception: `LineageStructureError` (so `FusionError` and `TimeFlowError`) is a `ValueError`, `UpdateRequiredError` a `RuntimeError`, `ProtectedPropertyError` an `AttributeError`
- **Logging:** Pycellin no longer adds a `NullHandler` to its logger, so warnings logged by Pycellin are shown on stderr by default
- **Dependencies:** matplotlib is no longer installed with Pycellin: install it yourself if your code uses it. Pycellin only needs it for the debug plots of the `RodWidth` and `RodLength` calculators (`debug=True`)

### Added

- **Model:** `merge()` to merge two models, and `split()` to split a model into several models from groups of lineage IDs. Properties reading an image, e.g. cell polygons from a label image, should be added to each model before merging: added to a merged model, they read the same image for all its lineages, with a warning
  - lineage ID collisions are resolved: the lineages whose ID is taken get new IDs, above the highest one in use
  - critical metadata (reference time property, time step and unit, pixel size, space unit) must match; other differing metadata values are stored as lineage properties
  - properties declared in both models must have the same property type, lineage type and unit, or `merge()` raises `ValueError`. A different data type only gives a warning, and the declaration of the model `merge()` is called on is kept
  - calculators that rely on external data (e.g. a label image) are not kept
  - if only one of the models has cycle lineages, the merged model gets cycle lineages for all its lineages
- **Model:** `rescale_time()` and `rescale_space()` to convert time or space values into another unit (e.g. frames to minutes, pixels to µm). Rescale right after loading: the properties added before are recomputed at the next `update()` but keep their unit, and a warning names those to add again. The other properties read from the file, e.g. TrackMate's `RADIUS`, keep their values and units
- **Model:** `remove_lineages()` to remove several lineages at once and return them, as `remove_lineage()` does for one
- **Model:** `relabel_cells()` to give cells consecutive IDs, optionally unique across the whole model
- **Model:** `remove_intercycle_links()` to remove the outgoing links of division cells
- **Model:** `get_cell_lineages()` and `get_cycle_lineages()` take an optional `lineage_ids` argument, to get only the lineages with these IDs, and raise `TypeError` for IDs that aren't integers. With `ignore_missing=False`, an unknown ID gives None instead of being skipped
- **Model:** `overwrite_lineage_id` argument to `add_lineage()`: given a lineage that has an ID, a different `lineage_id` raises `ValueError`, unless `overwrite_lineage_id=True`, which gives the new ID to the lineage and its cells
- **Model:** `lineage_props` argument to `to_cell_dataframe()`, `to_link_dataframe()` and `to_cycle_dataframe()` to include lineage properties in the DataFrame
- **Model:** `to_cycle_pair_dataframe()` to export pairs of related cell cycles with the properties of both side by side, e.g. to correlate the area at birth of mothers and daughters. The relation is any cycle property listing related cell cycles: `mother_cycle`, `daughter_cycles`, `sister_cycles`, `cousin_cycles`, or a user-defined one. `unique_pairs=True` keeps a single row for pairs listed from both sides, such as sisters
- **Metadata:** `label_image` and `label_image_path` standard metadata fields, for the label image of the model or the path to its TIFF stack: `add_cell_polygon()`, `add_cell_multipolygon()`, `add_cell_total_intensity()` and `add_cell_mean_intensity()` read them when given no label image
- **Metadata:** `ModelMetadata.diff()` to list the metadata fields that differ between two models
- **Properties:** `Property.get_incompatibilities()` to list the differences between two property declarations in property type, lineage type, unit and data type, where `float` and `float64` count as the same
- **Properties:** `time` core property (`create_time_property()`), the time of each cell, e.g. in minutes: `read_ctc()` and `from_trackpy()` compute it from the frames and the time step as their reference time property. Its `Time` calculator, in `pycellin.properties.core`, computes it from another time property and a factor, with `add_custom_property()`
- **Properties:** `cycle_start_time` and `cycle_end_time` core properties (`create_cycle_start_time_property()` and `create_cycle_end_time_property()`), the times of the first and last cells of the cycle in the reference time unit. Like `cycle_duration`, they are computed by `add_cycle_lineages()`
- **Properties:** `first_cell` and `last_cell` core properties (`create_first_cell_property()` and `create_last_cell_property()`), the cell IDs of the first and last cells of the cycle. `last_cell` has the same value as `cycle_id`, but says what it is. Like `cells`, they are computed by `add_cycle_lineages()`. Propagated to the cells, they pick the first or last cell of each cycle in `to_cell_dataframe()`: `df[df["cell_id"] == df["first_cell"]]`
- **Properties:** morphology properties `cell_polygon`, `cell_multipolygon`, `cell_area`, `cell_perimeter`, `cell_circularity` and `cell_solidity`, and `add_cell_contour()`
  - `cell_polygon` is computed from a label image or from cell contours (e.g. loaded from TrackMate or CTC data). From a label image, it keeps the largest piece of each label and fills its holes, with a warning listing the cells concerned
  - `cell_multipolygon` is computed from a label image and keeps every piece and hole of each label
  - `add_cell_contour()` computes `cell_contour` (`ROI_coords` in 0.5.1), previously only read from files, e.g. TrackMate or CTC data, from the cell polygons, e.g. to export to TrackMate the shape of cells segmented in a label image
- **Properties:** morphology properties `cycle_mean_area`, `birth_area` and `division_area`
- **Properties:** intensity properties `cell_total_intensity` and `cell_mean_intensity`, measured in an intensity image over the pixels of each cell, taken from a label image or from the cell polygons, minus an optional `background` value per pixel. To measure several channels, add them once per channel, each with its own image and `custom_identifier`
- **Properties:** intensity properties `cycle_mean_intensity`, `birth_intensity` and `division_intensity`
- **Properties:** the `add_*()` methods of properties computed from another property take its identifier as an argument (`polygon_prop`, `area_prop`, `displacement_prop`, `speed_prop`, `intensity_prop`), e.g. to compute `cell_area` from your own polygons. The unit of the new property is taken from that property
- **Properties:** `INPUT_PROPS` class attribute on calculators, to list the properties they read, e.g. `{"area_prop": ("node", "cell")}`. `add_custom_property()` checks that these properties are declared with the expected property and lineage types, for custom calculators too
- **Properties:** topology lineage properties `num_cells`, `num_cycles`, `num_divisions`, `num_gaps` and `num_leaves`
- **Properties:** topology lineage properties `lineage_cell_depth`, `lineage_cycle_depth` and `lineage_duration`
- **Properties:** topology cycle properties `mother_cycle`, `daughter_cycles`, `sister_cycles` and `cousin_cycles`, the IDs of the mother, daughter, sister and cousin cell cycles of each cell cycle. `mother_cycle` is None for root cycles, and `add_cousin_cycles()` takes a `degree`, like `get_cousins()`
- **Properties:** `location_tag`, a cell property read from a mask image. A `tag_names` dict maps pixel values to region names
- **Properties:** `normalized_age`, the relative age of a cell divided by the duration of its cell cycle, from 0 at the first cell of the cycle to 1 at the last one. With `ignore_incomplete_cycles=True`, the cells of cycles that start at the root or end with a leaf get NaN
- **Properties:** `uses_external_data()` class method on calculators, true for those that read data the model doesn't store, such as a label, intensity or mask image. `merge()` doesn't keep these calculators
- **Packaging:** `pc.__version__` gives the installed version of Pycellin
- **Exceptions:** `MissingPropertyError` (a `KeyError`), raised when a property that Pycellin needs is missing from the model or from a cell, e.g. when adding a property computed from one not declared yet, or plotting a property that some cells lack
- **Lineages:** `Lineage.get_depth()`, `Lineage.get_roots()`, `CellLineage.get_gaps()` and `CellLineage.get_duration()`

### Changed

- **Model:** core properties (`cell_id`, `lineage_id`, `timepoint` and the reference time property) are now protected in every model. Models read from GEFF files or built from scratch didn't protect all of them, so `remove_property()` could remove them
- **Model:** the warning about cell fusions when loading a file says how to list and correct them, with `get_fusions()` and `remove_link()`, instead of pointing to a documentation that doesn't exist yet
- **Model:** `add_cycle_lineages()`, `add_lineage()` with `with_cycle_lineage=True` and `merge()` no longer require the time step of the model, which building cycle lineages doesn't use. Without it, they raised `ValueError`, or for `add_lineage()` warned and skipped the cycle lineage. The `ValueError` of `update()` without a time step no longer says cycle lineages need it
- **Plotting:** in `CellLineage` and `CycleLineage` `plot()` and `get_tree_figure()`, nodes with a list of sizes in `node_marker_style` are drawn opaque and without outline, instead of as Plotly's semi-transparent bubbles with a white outline
- **TrackMate:** the reader declares `FRAME` with the unit "frame" instead of no unit
- **GEFF:** `write_geff()` writes the cell coordinates as space axes by default: `cell_x`, `cell_y`, and `cell_z` when it is declared, as long as every cell has a value for them, since GEFF axes can't have missing values (otherwise they are left out, with a warning). Pass `space_axes=[]` to write none. Without space axes, other GEFF tools couldn't place the cells, and `read_geff()` lost the space unit of the model
- **GEFF:** `write_geff()` writes the axes in the order of the GEFF specification, which follows OME-Zarr: time, channel, then space axes from z to x (e.g. t, z, y, x), as the dimensions of an image. `space_axes` still lists the x, y and z properties in that order, and the display hints are unchanged
- **Dependencies:** declare numpy, pillow, tifffile and geff-spec, which Pycellin imports directly but only got through other packages
- **Dependencies:** raise the minimum versions of pandas (2.2.2), scikit-image (0.24), shapely (2.0.4) and plotly (5.12) to the first ones that work with NumPy 2. The previous minimums allowed installs that failed at `import pycellin`
- **Dependencies:** raise the minimum versions of geff (1.1.4.1.1) and geff-spec (1.1.1). With earlier versions, GEFF files lost the unit, name and description of the properties
- **Dependencies:** the test dependencies moved from the `test` extra to a `test` dependency group, installed from a clone of the repository with `pip install -e . --group test` (pip >= 25.1)
- **Docs:** the "Creating a model from scratch" notebook, unfinished, and "Working with TrackMate data", covered by "Getting started", are removed. The other notebooks are updated and re-run, and "Custom properties" explains when a calculator should be local or global
- **Docs:** the README keeps only the `pip install` line of the installation steps, and links to the documentation for the rest: creating a conda environment, and installing the example notebooks or the development tools
- **Docs:** the docstrings of the exceptions, `Cell` and `PropertyType`, and the class docstrings of `Model`, `Data`, `Property`, `PropsMetadata`, `CellLineage` and `CycleLineage`, follow numpydoc's guide, with the types written as in the type hints and the default values given, e.g. `int | None, default=None`. Constructor parameters are documented in the class docstring, and `Model`, `Property`, `CellLineage` and `CycleLineage` get a description. The values of `PropertyType` and the fields of `Cell` are documented

### Fixed

- **Model:** changing the time step with `set_time_step()` corrupted the `timepoint` values
- **Model:** after `set_reference_time_prop()` (`set_reference_time_property()` in 0.5.1), `cycle_duration` kept the unit of the previous reference time property, although its values are computed from the new one
- **Model:** `add_lineage()` failed with `with_cycle_lineage=True` (`with_CycleLineage` in 0.5.1) or with a lineage that had no lineage ID, and ignored its `lineage_id` argument (`lid` in 0.5.1) when given a lineage. Given a lineage that has another ID, `lineage_id` now raises `ValueError`, unless `overwrite_lineage_id=True`
- **Model:** `add_lineage()` silently replaced a lineage that already had the same ID. It now raises `ValueError`
- **Model:** `split_lineage_from_cell()` silently replaced the lineage that already had the ID given as `new_lineage_id` (`new_lid` in 0.5.1), losing its cells. It now raises `ValueError`
- **Model:** `add_lineage()` and `CellLineage()` failed on an `assert` for a lineage ID that was a NumPy integer, e.g. taken from a DataFrame. They now accept it and, like `split_lineage_from_cell()`, store it as a Python integer, since a NumPy ID also made a later `add_lineage()` without an ID fail
- **Model:** `to_cell_dataframe()`, `to_link_dataframe()`, `to_cycle_dataframe()` and `to_lineage_dataframe()` raised a pandas `FutureWarning` when a numeric property was None everywhere in a lineage. With no lineage to export, the `ValueError` they raise now says so, instead of pandas' "No objects to concatenate"
- **Model:** with pandas 3.1 or later, `to_cell_dataframe()`, `to_link_dataframe()`, `to_cycle_dataframe()` and `to_lineage_dataframe()` raised a `Pandas4Warning`, since they used pandas' `inplace` argument, deprecated in pandas 3.1 and removed in pandas 4
- **Model:** the columns of `to_link_dataframe()` came in a different order in each Python session. They now keep the order in which the link properties were added
- **Model:** `add_cycle_lineages()` (`add_cycle_data()` in 0.5.1) silently kept the properties already declared under the identifiers of its cycle properties, e.g. cycle properties propagated to cell lineages in an exported file and loaded back, so Pycellin treated them as cell lineage properties. Such a declaration is now replaced when unused (no values in cell lineages, no calculator), and `add_cycle_lineages()` raises `ValueError` otherwise, asking to remove it first with `remove_property()`
- **Model:** adding a property already declared, e.g. calling an `add_*()` method again with other arguments, registered the new calculator but kept the first declaration. The declaration is now replaced too, with a warning. A property declared with another property type or lineage type is replaced only when unused, and raises `ValueError` otherwise
- **Model:** `update()` with a list of properties erased the values of the other cycle properties wherever it rebuilt cycle lineages (all of them after adding a property), left the other properties uncomputed on new or changed cells, and then reported the model as up to date. All the cycle properties are now computed again on rebuilt cycle lineages, and the model still requires an update, which computes the rest. A listed property without calculator, e.g. loaded from a file, made the update fail midway with `KeyError`: it is now ignored with a warning
- **Model:** a cell, link or lineage removed and then added back with the same ID before `update()` was still treated as removed: `update()` left the cell or link without property values, and deleted the lineage. This also happened without reusing an ID on purpose: once the lineage with the highest ID is removed, the next new lineage gets that ID back (the docstring of `get_next_available_lineage_id()` wrongly said it never does). So `update()` deleted a lineage split off with `split_lineage_from_cell()`, and left a lineage it split itself without cycle lineage and its new cells without property values
- **Model:** cells moved to another lineage, by a split in `update()` (e.g. after `remove_link()`), by `split_lineage_from_cell()` or by `add_link()` between two lineages, kept the `lineage_id` of their old lineage, so a GEFF file exported afterwards couldn't be read back correctly. `update()` now sets it. A split-off lineage also copied the lineage properties of the original lineage, e.g. TrackMate's track name, index and number of spots, so TrackMate exports had several tracks with the same name and index: it now starts with its new ID only
- **Model:** `update()` failed with `KeyError` when cells or links added since the last update had been moved to another lineage by `add_link()`, or when a link had been added to a lineage removed since
- **Model:** `update()` didn't update the cycle properties propagated to the cells with `propagate_cycle_properties()`, although the "Managing properties" notebook said it did: after a change, e.g. `remove_link()`, the cells kept the values of their former cell cycle, and cells added later got none. `update()` now copies them again once computed on the cycle lineages. Only the properties propagated that way are copied, and `propagate_cycle_properties()` without `props` now leaves out the properties of lineage type `"both"` (`"Lineage"` in 0.5.1), whose cell values it overwrote with those of the cycles
- **Model:** `add_custom_property()` used the `Property` of the calculator as the declaration of the model, which Pycellin then changed in place: after `propagate_cycle_properties()`, its lineage type was `"both"` (`"Lineage"` in 0.5.1), also in every other model given the same `Property`, even before their own propagation. The model now keeps its own copies of the calculator and of its `Property`, so they can be given to several models. Changing them after adding no longer changes the model: change the declaration returned by `get_property()` instead
- **Model:** `add_pycellin_properties()` given a dictionary instead of a list, as the "Managing properties" notebook showed, silently ignored the arguments of the properties, e.g. angles came in radians instead of degrees. It now raises `TypeError`, as it does for a string, which it split into letters, and for list items other than strings and dictionaries, which it skipped. No property is added then
- **Model:** TrackMate and GEFF data where separate cells merge, i.e. a cell fusion that gives its lineage several roots, couldn't be loaded: the readers failed with an `UpdateRequiredError` about root nodes, which didn't mention fusions. Like other fusions, they are now loaded with a warning, and `get_fusions()` and `remove_link()` can be used to correct them
- **Model:** the `FusionError` of `get_cell_cycle()`, and so of `get_cell_cycles()` and `add_cycle_lineages()` (`add_cycle_data()` in 0.5.1), could name the wrong cell: the cell it started from instead of the one with several parents
- **Model:** the `FusionError` of `add_link()` between two lineages named the source lineage, although the cell it was about is in the target lineage. It also said this cell had more than one parent, when it had one and the link was refused
- **Model:** the `TimeFlowError` of `add_link()` said the target cell had a time value lower than its parent's, also when both cells had the same time
- **Model:** `add_link()` between two lineages with cell IDs in common, e.g. with the default IDs of `add_cell()` or after the new `relabel_cells()`, could lose cells. The cells of the target lineage given a new ID, to avoid the IDs of the source lineage, could get the ID of another of the cells moved and merge with it: `add_link()` then failed with an unclear error after removing the cells from the target lineage, or silently kept one cell instead of two. New IDs now skip the IDs of the cells moved too
- **Properties:** `turning_angle` (`angle` in 0.5.1), `absolute_age` and `relative_age` were recomputed for every lineage at each update, as their calculators were global instead of local
- **Properties:** `turning_angle` (`angle` in 0.5.1) was declared as an edge property although its values are on cells
- **Properties:** `cycle_mean_displacement` and `cycle_mean_speed` (`branch_*` in 0.5.1) raised a NumPy `RuntimeWarning` for cell cycles without links. They are now NaN without warning
- **Properties:** `cell_displacement`, `cell_speed`, `turning_angle` (`angle` in 0.5.1) and `straightness`, and the cycle properties computed from them, failed with `KeyError` on 2D models without `cell_z`, e.g. loaded from CTC label images or a GEFF file. They now use `cell_x` and `cell_y`, plus `cell_z` when it is declared
- **Properties:** `cell_displacement`, `cell_speed`, `turning_angle` (`angle` in 0.5.1) and `straightness` could be added to a model without cell coordinates, e.g. read from a CTC file without label images, and `update()` then failed with `KeyError: 'cell_x'`: the model couldn't be updated or exported until they were removed. They now raise `MissingPropertyError` when added, as does `location_tag`. A cell without coordinates, e.g. added with `add_cell()`, gave the same `KeyError` at update: the `MissingPropertyError` raised now names the cell, its lineage and the property
- **Properties:** `Property()` raised `KeyError` on an unknown property type, e.g. `prop_type="nodes"`. It now raises the `ValueError` it raises for other invalid property types, which lists the valid ones and now also gives the value received
- **Properties:** `PropsMetadata()` drops the protected properties that aren't declared, with a warning, but missed every other one of them in a row, e.g. the second one in `protected_props=["a", "b"]`, which stayed protected. It also removed the ones it dropped from the list given as `protected_props`
- **Plotting:** `CellLineage` and `CycleLineage` `plot()` and `get_tree_figure()` modified the `node_marker_style` dict given to them, adding the node colors of `node_colormap_prop` to it: the same dict reused for another lineage gave it the colors and color bar of the previous lineage
- **TrackMate:** `turning_angle` (`angle` in 0.5.1) in degrees was exported as a TrackMate angle, which TrackMate reads as radians
- **TrackMate:** `division_rate` was exported as a time, so TrackMate showed it in the time unit, and the reader read it back with that unit, e.g. "minute" instead of "1/minute". It is now exported as a rate. The reader, which failed with `ValueError: Invalid dimension: RATE` on features with that dimension, reads them in 1 over the time unit
- **TrackMate:** the writer declared the properties that TrackMate and Pycellin don't know, e.g. custom ones, with the dimension NONE and a warning, whatever their unit. Those in pixels are now declared as lengths, or positions when named `x`, `y` or `z`, and those without unit or in frames as NONE without warning. Other units still give NONE with the warning
- **TrackMate:** the writer declared integer properties as non-integer features when their data type wasn't spelled `int`, e.g. `int64` in models read from GEFF files, so Pycellin read `FRAME` and `VISIBILITY` back as floats
- **TrackMate:** with `keep_all_spots=True` and `keep_all_tracks=True` (now `lone_spots="all"` and `tracks="all"`), spots without a track got lineage IDs already used by tracks, so some lineages were silently lost: FakeTracks loaded as 26 cells in 11 lineages instead of 107 in 18. They now get the next IDs after those of the tracks
- **TrackMate:** the writer wrote missing values (None) as the string 'None', which TrackMate can't read. They are now written as NaN, which the reader reads back as None for integer properties instead of failing
- **TrackMate:** without `propagate_cycle_props=True`, the writer declared the cycle properties as spot features although no spot had their values. In the reloaded model, these declarations remained after `add_cycle_lineages()` (`add_cycle_data()` in 0.5.1), so Pycellin treated the cycle properties as cell lineage properties: `propagate_cycle_properties()` skipped them, or raised when they were listed. Cycle properties are now only declared when propagated
- **TrackMate:** the reader failed on files without `POSITION_T`, which TrackMate doesn't require. It is now computed from `FRAME` and the frame interval of the image, with a warning
- **TrackMate:** the writer failed with `KeyError` on a model loaded from TrackMate to which a lineage had been added, since that lineage had no `FilteredTrack` flag. A lineage without the flag is now exported as a visible track
- **TrackMate:** the writer took every lineage with a negative ID for a one-cell lineage and wrote no track for it, so such a lineage with several cells lost its track and links, e.g. a cell cut off by `remove_link()`, which got minus its ID as lineage ID, then linked to a new cell. A lineage is now written as a track whenever it has several cells, whatever its ID
- **TrackMate:** a model loaded from a TrackMate file with cells without contour (`ROI_N_POINTS` of 0, as the writer writes them) couldn't be exported to TrackMate again: their contour, loaded as None, made the writer fail with `TypeError`
- **TrackMate:** the reader failed with "Invalid data type: unknown" on files with an attribute that their FeatureDeclarations don't declare, as soon as two spots, edges or tracks had it: trackpy models exported by Pycellin, or files written by other tools. On a single element, the attribute was declared with the `unknown` data type and kept as text. Such attributes are now loaded with the data type of their values (integer, float or text) and no unit, with one warning naming them
- **TrackMate:** the writer wrote the attributes of cells, links and lineages that have no property declaration, without declaring them, and TrackMate reads every spot attribute as a number, so a text one kept it from opening the file. They are now left out, with a warning naming them
- **TrackMate:** `keep_all_spots=True` (now `lone_spots="all"`) had no effect without `keep_all_tracks=True`: the spots outside tracks were removed along with the tracks hidden by the track filters of TrackMate
- **TrackMate:** the reader failed with `UnboundLocalError` on files without a `FilteredTracks` tag, which other tools may not write. All their tracks are now visible
- **TrackMate:** in files with the spots after the `FilteredTracks` tag, as other tools may write them, the reader lost every cell of the tracks and kept the spots outside tracks instead, each as a one-cell lineage: FakeTracks written in that order loaded as 23 one-cell lineages instead of 84 cells in 2 lineages. The spots and tracks are now filtered once the whole file is read
- **TrackMate:** the writer wrote every spot as visible (`VISIBILITY` of 1), so after a round trip TrackMate showed the spots its spot filters had hidden, e.g. loaded with `keep_all_spots=True` and `keep_all_tracks=True`. Cells now keep their `VISIBILITY`, and cells without one are visible
- **TrackMate:** the writer declared a string property called `name` as a feature, so the reader failed on the exported file with `could not convert string to float`. It is now only written as the display name of spots or tracks, and the reader ignores such a declaration
- **TrackMate:** the writer failed with `NetworkXUnfeasible` on some models with cell IDs repeated across lineages: it renumbers the cells of such models, which failed when that swapped IDs, e.g. cell 0 becoming cell 1 and cell 1 becoming cell 0. This is common after the new `relabel_cells()`
- **TrackMate:** exporting a model with cycle lineages without `propagate_cycle_props=True` warned that `cells` wasn't numeric and wouldn't be supported by TrackMate, as if the other cycle properties were exported, although none is. As for GEFF, a warning now names the cycle properties left out and says how to export them
- **GEFF:** the reader silently kept only one lineage when several disconnected parts of the graph had the same lineage ID. It now raises `ValueError`, except when the lineage ID was only inferred from a `lineage_id` property of the file: lineage IDs are then autogenerated
- **GEFF:** the reader kept lineage IDs that weren't integers: floats became the IDs of the model, which broke `add_lineage()` and which the lineage getters refuse, and strings made it fail with an unclear `TypeError`. A property whose values aren't all integers can no longer identify lineages: lineage IDs are autogenerated, with a warning, and the values stay in the property
- **GEFF:** the reader overwrote the `cell_id` and `lineage_id` properties of the file (`cell_ID` and `lineage_ID` in 0.5.1) when it didn't use them as identifiers. They are now kept as `geff_cell_id` and `geff_lineage_id`, with a warning
- **GEFF:** without display hints in the file, the reader took the first space axis as x, the second as y and the third as z. But GEFF orders the axes like OME-Zarr, as the dimensions of the image, with x last, so files written by geff's own CTC converter (t, y, x) or by ultrack (t, z, y, x) loaded with x and y, or x and z, swapped, and no warning. Axes named `x`, `y` or `z` (in any case) or ending with `_x`, `_y` or `_z` (e.g. `POSITION_X`) are now used for that coordinate. Only the other space axes are assigned by position, as in OME-Zarr where x comes last, with a warning, and several axes named for the same coordinate raise `ValueError`
- **GEFF:** the reader lost coordinate values when a coordinate was read from a property named like another Pycellin coordinate, e.g. with `cell_x_prop="cell_y", cell_y_prop="cell_x"`, which left the model without `cell_x`
- **GEFF:** the reader failed with `NetworkXUnfeasible` on files whose cell IDs swap some node IDs, e.g. node 0 with cell ID 1 and node 1 with cell ID 0
- **GEFF:** the writer didn't write the metadata of properties with several types (`LINEAGE | NODE`, `LINEAGE | EDGE`)
- **GEFF:** the writer failed with a `RuntimeError` that named no property on cell or link properties whose data type GEFF can't store, such as `cells` after `propagate_cycle_properties()` or TrackMate features loaded with the `unknown` data type, and on None values. Such properties are now skipped with a warning naming them, and None values are written as missing values
- **GEFF:** the writer declared `cycle_id` (`cycle_ID` in 0.5.1) as the tracklet property of every model with cycle lineages, but cells only have it once propagated, so most files declared tracklets they didn't contain. Even propagated, the values could be out of date or repeated across lineages (e.g. after `merge()`), which fails geff's tracklet validation. A tracklet property is now only declared with `tracklets=True`, which writes its own `tracklet_id` property
- **GEFF:** on every export of a model with cycle lineages, the writer warned that the cycle properties had "no corresponding data" and "will be removed from the model metadata". They do have values, they just aren't exported, and the model keeps them. The warning now says that, and how to export them with `propagate_cycle_props=True`. Properties without any value, e.g. those that TrackMate declares without using them, only get an INFO message now, and lineage properties, which are never exported, no message at all
- **CTC:** the reader gave cells no `timepoint`, although it was the reference time property, and no `lineage_id`
- **CTC:** the reader failed on labels with holes or made of several pieces. Their contour is now the outline of the largest piece, holes filled, and a warning lists them
- **CTC:** loading label images (`labels_path`):
  - each contour went to the cell whose ID is the label value, instead of the cell of that label in that frame, so most cells had no contour, and the others generally had the contour of another cell
  - reading the pixel size from them failed with `KeyError`. It is now read from their resolution, in the unit of the ResolutionUnit tag or of the ImageJ metadata. A resolution without unit is ignored, and so is one in inches, most likely a print default such as 72 dpi, with a warning
  - each label was matched to its cell by scanning all the cells, so the loading time grew with the square of their number (over a minute for 8,000 cells). It now grows linearly
  - 3D label images failed with "too many values to unpack", and a stack holding all the frames with that error or, when its name had no frame number, with "Can't parse frame value". The reader now says that only 2D label images, one per frame, are supported
  - a `labels_path` that wasn't a folder was silently ignored when the space unit and pixel sizes were given, leaving cell positions and contours declared without values. It now raises `ValueError`
  - the `label_images_location` metadata field (`label_imgs_location` in 0.5.1) was missing when the space unit and pixel sizes were given
- **CTC:** the writer wrote negative frames for cells with negative timepoints, e.g. in a lineage added with earlier times than the rest of the model. It now raises `ValueError`, giving the smallest `frame_offset` that avoids them
- **trackpy:** the reader failed when given a `time_step`, which it applied to frames, and gave cells no `lineage_id`
- **trackpy:** the reader mishandled the DataFrame columns named like the properties it creates: it silently overwrote `cell_ID` and `timepoint`, and kept `lineage_ID` as it was, in floats, even where it contradicted the lineages. It now raises `ValueError` for columns named `cell_id`, `lineage_id` or `timepoint`
- **trackpy:** the reader didn't declare the DataFrame columns other than `frame`, e.g. `particle`, `mass` or `size`: they were on the cells but missing from the properties of the model, and a model exported to TrackMate couldn't be loaded back. Every column is now declared with its data type: trackpy's own columns get a description, and the sizes and static errors (`size`, `ep`...) the unit of the coordinates. When all the columns were numbers, integer columns were also loaded as floats
- **trackpy:** the reader declared the coordinates as `cell_x` and `cell_y` but stored them as `x` and `y`, so the properties computed from them, e.g. `cell_displacement`, failed with `KeyError: 'cell_x'`. They are now stored as `cell_x` and `cell_y`, plus `cell_z` in 3D
- **trackpy:** the reader linked the cells by scanning all of them for each particle, so the linking time grew with the square of the number of rows: loading 40,000 rows took 14 s, now 3 s
- **trackpy:** with pandas 3.1 or later, the writer raised `Pandas4Warning`s, since it used pandas' `inplace` argument, deprecated in pandas 3.1 and removed in pandas 4
- **trackpy:** exporting a model without divisions, e.g. one loaded from trackpy, warned that the model was already up to date
- **Packaging:** the PyPI page had broken links: Documentation and Examples led to a site that doesn't exist, the README links to the notebooks didn't open them, and the README logo didn't show. Examples now opens the notebooks on GitHub, Documentation opens the new documentation site, and a Changelog link is added
